# PyTorch accelerators

LeRobot supports multiple hardware acceleration options for both training and inference.

These options include:

- **CPU**: CPU executes all computations, no dedicated accelerator is used
- **CUDA**: acceleration with NVIDIA & AMD GPUs
- **MPS**: acceleration with Apple Silicon GPUs
- **XPU**: acceleration with Intel integrated and discrete GPUs

## Getting Started

To use particular accelerator, a suitable version of PyTorch should be installed.

For CPU, CUDA, and MPS backends follow instructions provided on [PyTorch installation page](https://pytorch.org/get-started/locally).
For XPU backend, follow instructions from [PyTorch documentation](https://docs.pytorch.org/docs/stable/notes/get_start_xpu.html).

### Verifying the installation

After installation, accelerator availability can be verified by running

```python
import torch
print(torch.<backend_name>.is_available())  # <backend_name> is cuda, mps, or xpu
```

## How to run training or evaluation

To select the desired accelerator, use the `--policy.device` flag when running `lerobot-train` or `lerobot-eval`. For example, to use MPS on Apple Silicon, run:

```bash
lerobot-train
    --policy.device=mps ...
```

```bash
lerobot-eval \
    --policy.device=mps ...
```

However, in most cases, presence of an accelerator is detected automatically and `policy.device` parameter can be omitted from CLI commands.

## Mixed precision

Training precision is owned by `--accelerator.mixed_precision`, which accepts `no` (default), `bf16` and `fp16`:

```bash
lerobot-train \
    --policy.type=act \
    --accelerator.mixed_precision=bf16 ...
```

`fp16` requires an accelerator: it is rejected on `--policy.device=cpu`, where accelerate builds no loss scaler and the run would silently fall back to full precision. `bf16` autocasts on CPU too, so it is not restricted.

`bf16` requires hardware support (Ampere or newer on NVIDIA GPUs). On older accelerators such as V100 or T4, use `fp16`.

### fp16 and the loss scaler

`fp16` has a much smaller exponent range than `bf16`, so gradients are scaled up before the backward pass and scaled back down before the optimizer step. LeRobot delegates this to accelerate's `GradScaler`, which also detects overflowing gradients and skips those optimizer updates. Under sharded training the gradients are `DTensor`s and PyTorch reduces the overflow flag across the device mesh, so an overflow on one rank skips the update on all of them.

Skipped updates are normal, especially in the first few steps while the scale calibrates down from its initial value. They are visible in the logs as the `scale` metric dropping. The scale is saved with every checkpoint (`training_state/scaler_state.json`) and restored on resume, so a resumed run does not have to recalibrate.

The scaler can be tuned if the defaults do not suit a policy:

```bash
lerobot-train \
    --policy.type=act \
    --accelerator.mixed_precision=fp16 \
    --accelerator.grad_scaler.init_scale=1024 \
    --accelerator.grad_scaler.growth_interval=2000 ...
```

## torch.compile

`lerobot-train` can compile the policy with `torch.compile`. It is off by default; turn it on with `--use_torch_compile=true`:

```bash
lerobot-train \
    --policy.type=act \
    --policy.device=cuda \
    --use_torch_compile=true ...
```

- `--torch_compile_backend` (default `inductor`) and `--torch_compile_mode` (default `default`) are passed to `torch.compile`. These are the same flag names as in `lerobot-rollout`. The modes `reduce-overhead`, `max-autotune` and `max-autotune-no-cudagraphs` apply to the `inductor` backend.
- The first training steps are slow while the model compiles, so a speedup only shows after the warm-up. Whether you gain anything depends on the policy, the GPU and the batch size: compare `updt_s` in the logs with and without the flag before you keep it on.
- The model is compiled with static shapes (`dynamic=False`). Each new batch size gets its own graph, and the usual batch size keeps its own graph:
  - At the end of the first epoch, the smaller last batch (the dataloader keeps it) compiles once more, so that step is slow. Later epochs reuse that graph.
  - The first eval-loss step (`--eval_steps`) also compiles once more, because it runs without gradients.
- With static shapes, code that runs after a `.item()` call is compiled for each new Python value it sees. For ACT this is the small loss computation at the end of `forward`. It recompiles on each of the first steps until torch reaches its recompile limit (8), then torch logs a `torch._dynamo hit config.recompile_limit` warning and runs that part without compile. This is expected and costs little: the model itself stays compiled.
- The model is compiled in place (`nn.Module.compile`), so checkpoints are the same as without compile. A checkpoint trained with compile loads in `lerobot-rollout` and `lerobot-eval` as usual, and you can resume a run with the flag on or off.
- If `torch.compile` is not available, cannot be set up, or fails to compile during the **first** training step (for example, no Triton or C compiler is installed), training logs a warning and continues without compile. Other errors in that step, such as CUDA out-of-memory, stop training as usual. A compile failure later in the run (at one of the recompiles above) also stops training with an error; restart or resume without the flag.
- On PyTorch 2.10 and newer, the first step also compiles the backward pass during the forward pass, so the fallback works in multi-GPU (DDP) runs too. On older PyTorch versions, a compile failure in the backward pass of a multi-GPU run may not recover.
- With `inductor`, the losses are not bit-identical to a run without compile, because dropout draws different random numbers. Only the random draws differ.
- It is not applied to sharded (FSDP2) training yet. `--accelerator.compile.*` is a separate placeholder for that future sharded path and does not affect this flag.

## TF32 and channels_last

Two more optional speed-ups for training on NVIDIA GPUs. Both are off by default. They do not change the checkpoint format. Like `torch.compile`, the gain depends on your policy, GPU and batch size, so **measure it**: compare `updt_s` in the logs (after the first steps) with and without the flag before you keep it on.

```bash
lerobot-train \
    --policy.type=act \
    --policy.device=cuda \
    --accelerator.mixed_precision=fp16 \
    --use_tf32=true \
    --use_channels_last=true ...
```

Mixed precision is set with `--accelerator.mixed_precision=fp16` (or `bf16`; the default `no` trains in float32). `lerobot-train` does not read `--policy.use_amp`, so that flag does not turn on mixed precision in training.

### `--use_tf32`

- At the start of training it sets `torch.backends.cuda.matmul.allow_tf32 = True`, `torch.backends.cudnn.allow_tf32 = True` and `torch.set_float32_matmul_precision("high")`, and logs the result. TF32 is a faster float32 mode of the tensor cores on Ampere (RTX 30xx, A100) and newer GPUs. It keeps the float32 range but rounds to fewer digits.
- It only applies to CUDA. On other devices it logs that it does nothing.
- Expect a small gain, or none:
  - `lerobot-train` already turns on TF32 for matmuls (`torch.backends.cuda.matmul.allow_tf32 = True`) in every run, and PyTorch already allows TF32 for cuDNN convolutions by default. The flag makes this explicit and logged, and keeps it on if those defaults change.
  - With mixed precision (`--accelerator.mixed_precision=fp16` or `bf16`), most matmuls and convolutions already run in that lower precision. TF32 only affects the operations that stay in float32.

### `--use_channels_last`

- It converts every 2D conv layer of the policy to the `torch.channels_last` memory format. For ACT, that is the ResNet image backbone (and the 1x1 conv after it). A forward pre-hook on each conv layer also gives it its image input in `channels_last`. Only the memory layout changes, not the values, so the model computes the same thing (up to float rounding).
- It helps most with mixed precision (`--accelerator.mixed_precision=fp16` or `bf16`): the float16 and bfloat16 conv kernels of the tensor cores work in `channels_last`. Without `channels_last`, cuDNN may have to reorder the data around each conv. In float32 training the gain is usually smaller.
- It works with mixed precision and with `--use_torch_compile=true`. The conversion happens before the model is compiled. With the `inductor` backend, torch may already choose `channels_last` for convs by itself, so the gain on top of compile can be small.
- Checkpoints are saved in the standard layout, with the same values. They load as usual in `lerobot-rollout` and `lerobot-eval`, which do not need the flag. You can resume a run with the flag on or off.
- If the policy has no 2D conv layers, it logs that it does nothing. It is tested with ACT. It is not applied to sharded (FSDP2) training yet.
